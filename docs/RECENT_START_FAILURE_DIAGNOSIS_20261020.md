# 近期无法启动：执行记录与双串口诊断（2026-10-20）

## 结论与证据范围

**本次复现任务 `142:74` 的启动失败由启动握手超时引起：从机已执行开阀，主机仍在等待首个租约确认；确认到达之前，固定 2400 ms 启动窗口已到期，主机取消任务并关闭从机。主机没有输出启泵命令，最终脉冲为零。**

传输本身有明显时延：启动确认占用分段发送通道，随后一条同任务的重复命令确认继续占用该通道，首个租约确认排队 459 ms，再发送 649 ms。主机最终收到的是匹配序号且 `result=OK` 的回复，但已经进入取消收尾阶段，`applied=0`。

本次没有发现 Mesh 发送资源耗尽、业务发送错误或节点离线的证据。当前主机运行去除 build 白名单后的固件，本次原因是 `TRANSPORT`，与之前任务 `141:62` 的白名单 `PROTOCOL` 拒绝不同。

APP 最终快照共有 19 条记录。新 epoch `142` 的最近 12 次中，5 次为零脉冲 `TRANSPORT`，7 次有流量记录，但这 7 次也均以异常结算。历史任务 `142:65/69/70/71` 缺少全过程日志，只能确认与本次失败表象一致，不能认定已逐次证明同一根因。

### 从机为什么没有及时回完确认

以下全部采用从机自己的时钟：

| Ticket / 报文 | 排队 t | 实际提交 t | 分段结束 t | 排队耗时 | 分段占用 |
|---|---:|---:|---:|---:|---:|
| 321 / CommandAck | 672952 | 672952 | 673312 | 0 ms | 360 ms |
| 322 / CommandAck | 673402 | 673404 | 674520 | 2 ms | **1116 ms** |
| 323 / CommandAck | 673477 | 674521 | 675167 | **1044 ms** | **646 ms** |
| 324 / LeaseAck seq 204 | 674714 | 675173 | 675822 | **459 ms** | **649 ms** |
| 325 / CommandAck | 673865 | 675823 | 677337 | **1958 ms** | 1514 ms |

关键关系：

1. 首次开阀与 ticket 322 的 CommandAck 入队同在 t=673402，与从机 `Start` 处理后发送确认的代码一致。
2. ticket 322 尚未结束时，另一个同任务 CommandAck 已在等待。它在 ticket 322 结束的下一毫秒占用了通道。
3. LeaseAck 入队 t=674714 时，ticket 323 正在分段发送。LeaseAck 必须等到该发送结束后才提交。
4. 虽然 LeaseAck 的队列优先级高于 CommandAck，但调度器无法抢占已经提交的同 peer 分段发送，因此“提升优先级”本身不能消除这 459 ms 等待。
5. 主机发了 2 次 Prepare、3 次 Start，从机产生多条确认。现有 `mesh_tx` trace 未记录 CommandAck 内的 command/result，无法仅凭这些 trace 精确标注每条 cf 确认对应的是 Prepare 还是 Start；同任务重复确认占用通道的事实不依赖这个细分。

主机看到的租约往返时间 1283 ms，采用主机同钟计算。从机的 459+649 ms 只表示其队列和发送占用，不能把两块设备的绝对 t 相减来补出其他延迟，也不能把 SAR 结束时刻等同于业务层收到回复。

## 对应代码与两个时间预算

| 机制 | 代码位置 | 当前行为及影响 |
|---|---|---|
| 首次实际 Start 启动计时 | `src/master_scheduler.cpp:174`，尤其 189 行 | 重试不会延长 bootstrap，避免无界等待 |
| 命令重试 | `src/master_scheduler.cpp:292` | 首次等待 300 ms，随后 600、1000 ms；现场确认分段占用超过 1 秒，容易在原确认返回前产生重试 |
| 何时发送 Lease | `src/master_scheduler.cpp:249` | 只有 `opened_` 已置位才发送；本次首 Lease 比首 Start 晚 1397 ms |
| 启动总预算 | `src/master_scheduler.cpp:319` | 从首 Start 起固定 2400 ms；另有 Opening 阶段 4000 ms 外层期限，前者先触发 |
| 启泵租约新鲜度 | `src/master_scheduler.cpp:326` | 必须全部确认，并且 `now - leaseAckAt <= 1000 ms` |
| leaseAckAt 含义 | `src/master_scheduler.cpp:226`，尤其 244 行 | 存的是对应 Lease 的实际提交时间，不是回复接收时间 |
| 取消后的确认 | `src/master_scheduler.cpp:226` | abort 或已进入 Draining 时拒绝应用，符合本次 `applied=0` |

**因此至少有两个不同瓶颈：启动总窗口 2400 ms，以及启泵时租约往返年龄 1000 ms。** 本次直接触发的是前者；首个确认实际年龄为 1283 ms，即便只延长总窗口，该确认也已经不能单独满足原来的启泵新鲜度条件，还要等待后续足够新的确认。

不能把“运行期 LeaseAck 等待上限已是 8000 ms”理解为启动也有 8000 ms。启动路径仍额外限制 2400/1000 ms。

## 能启动的对照任务与尾流问题

任务 `142:73` 的首 Start 在主机 t=645959 提交，首个有效 LeaseAck 于 t=647136 到达，往返年龄 352 ms。主机在同一 t 输出启泵，首 Start 到启泵 **1177 ms**，满足现有两个门槛。

该任务随后有连续脉冲，200 mL 设置最终记录 1296 脉冲、折算 220 mL，原因 `TAIL_FLOW`。从机关阀命令 t=666511，到尾流 Fault t=669517，相隔 3006 ms，符合本地 `settleLimitMs=3000`：在限期内没有获得连续 500 ms 的脉冲安静窗口。

这说明尾流异常与本次无法启泵需要分别处理：

- `142:73` 从机关阀命令后约 3.2 秒，主机才记录停泵命令；该间隔依据双串口接收时间，只取近似值。
- 从机 `Application::status()` 当前只允许发送 Done/Fault；Target 关阀后进入 Settling 时，即使 Lease 分支调用 `status(true)`，也不会立即上报该关闭状态。主机因此可能要等终态才知道该路已关闭，这是代码可确认的反馈缺口。
- 缺少及时关阀反馈会延迟主机对“全部阀门已关闭”的判断，应作为独立修复项；现有证据不能进一步断言尾流全由它引起。
- 关阀后的脉冲可能来自真实残流、阀门未完全关闭或电气干扰，尚无机械位置、压力、流量示波或量杯数据，不能选定某个硬件原因。
- 前一任务 Fault 不会永久锁住新任务：任务 74 已完成准备并执行开阀，排除了本次被旧 TAIL_FLOW 状态直接拒绝的解释。

## 可实施的修复顺序与验收

本轮只做诊断和证据整理，没有修改固件业务逻辑或调整保护参数。

1. **先补足启动诊断字段。** 在主机 CommandAck 接收处记录 command、reply、applied；在停止处明确 `BOOTSTRAP_TIMEOUT / COMMAND_REJECT / TX_ERROR / ACK_TOO_OLD` 等内部触发点及对应时间。保留对外原因码兼容性，让下一次不再只得到笼统 TRANSPORT。
2. **减少启动确认的重复分段。** 按已测到的命令往返分布设置有界重试，避免 300 ms 在正常大于 1 秒的确认过程中连续制造重试。收到对应确认或进入后续阶段时，清理仍在本端待发的旧阶段请求；从机对已被后续阶段证明收到的旧阶段成功确认进行有状态合并。不得伪造结束或撤销已经交给 SDK 的在途 ticket，也不得吞掉非 OK 拒绝和必须回复的丢包重试。
3. **一起设计启动总期限和租约新鲜度。** 用 1/2/5 路的端到端时延分位数及上界确定参数，并与从机开阀无流等待 5000 ms、租约 12000 ms、运行期确认期限 8000 ms 一并校验。保留从首 Start 开始的固定总期限；不得通过重试滑动延长，也不能把回复接收时间当作 Lease 的签发时间来虚增有效期。仅改 2400 ms 不是完整修复。
4. **独立补齐“已关阀、正在收尾”的及时反馈。** 必须与最终计量 Result 分开表达，主机收到全部关闭确认后及时停泵，继续等待尾流结算；新消息若改变线协议需更新协议版本及能力校验。仍要保留关阀后计量、最终结果持久化和无确认时停机保护。

建议为这轮修复增加以下验收条件；它们尚未执行，不能当作已经通过：

- 将本次关键时序做成 host 回归场景：Start 确认占用 1116 ms、后续重复确认占用 646 ms、LeaseAck 排队 459 ms、主机首租约往返 1283 ms。新版必须在声明支持的时延范围内正常启动，或给出可识别的启动超时原因。
- 分别覆盖新鲜度超限但未超过总期限、迟到 OK、重复 ACK、关闭后迟到 ACK、任务序号乱序、发送器故障、部分节点无回复。未确认、过期或已取消的任务都不能启泵。
- 对尾流反馈验证主机及时停泵且最终计量仍完整；反馈丢失时仍有固定期限保护，不得以重复启动补抽。
- 台架单路至少 50 批，再做 2 路和最多 5 路，记录每路首 Start、StartAck、首 Lease、首 LeaseAck、启泵的真实时刻和失败触发点。容量和时延的声明必须与实测范围一致。
- 有脉冲的批次仍须检查主从最终原因、实际量杯水量和关阀后脉冲，不能只用“泵成功启动”验收整个抽水功能。
