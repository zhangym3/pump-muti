本文保留初次 08:09 双端采集的结论和 8 条任务快照。后续任务 315:84/85、用户提供的 315:87 从机日志及真实控制代码复现，见 [异常停止深入诊断](DEEP_STOP_DIAGNOSIS_20261021.md)。

## 1. 结论及证据范围

**初次完整捕获的双端任务 `315:83`：现场有出水，但从机 GPIO5 的已接受脉冲累计值没有增长，开阀约 5 秒后触发 `NO_FLOW` 保护。** 用户已确认“泵阀动作，有出水”。该结果把排查重点收敛到传感器、接线、电平、实际流经传感器的水流，以及 GPIO 中断采集链路；尚不能仅凭日志断定某根线断开或传感器损坏。

此外，存在独立的通信异常证据：首次 START 后的 StartOK 未出现在主机接收日志，1500 ms 重试后才收到；运行期 LeaseAck 的 seq=23、24 已被从机协议栈接受发送，但主机没有对应 `lease_rx`。当前日志不能区分空口丢失、主机底层接收丢弃和串口记录缺失。不能将全部历史失败都归因于霍尔，也不能将最新一次 `NO_FLOW` 归因于 Mesh 完全未启动。

本次读取真实手机的 8 条历史任务，并采集 COM3/COM4 约 90 秒（北京时间 08:09:10～08:10:40）。仅发送 `hello`、`local`、`nodes`、`hall` 和最新任务的 `query`；任务 `315:83` 由用户在采集期间通过 APP 发起。采集结束串口已关闭。

## 5. 脉冲链路核查

当前从机源码：

- `include/board_profile.h`：阀输出 GPIO4；流量输入 GPIO5；GPIO6 外部联锁禁用。
- `src/hardware.cpp`：GPIO5 输入、内部上拉、下降沿中断；IRAM ISR 增加计数；`flow()` 与 HALL 日志读取同一累计计数，受临界区保护。
- `src/flow_job_controller.cpp`：START 在开阀前读取 baseline；任务脉冲等于累计计数减 baseline；无首脉冲 5000 ms 关阀；已有脉冲后中断流量 1500 ms 关阀。
- `src/application.cpp`：HALL 日志在应用层按秒输出，没有在 ISR 内打印。对项目 src/include 的检查未发现其他重配 GPIO5 的调用。

因此，最新任务不是仅 APP 漏显示、换算 k 错误或 baseline 把已增长计数清零：本地 raw 本身没有增长。100 μs 过滤相当于约 10 kHz 的接受频率上限，尚无证据说明它导致普通流量脉冲全部被滤掉。每秒采样 level=1 只是瞬时电平，不能替代波形测量；raw 不变说明没有新增被接受的下降沿，具体是未形成边沿还是采集遗漏仍需验证。

现场检查按下列顺序进行：

1. 按传感器实际型号核对供电规格、VCC/GND/信号定义及共地，确认信号线接的是板上丝印 **GPIO5**，不是排针第 5 位。GPIO6 无需额外跳线。
2. 确认出水确实经过该传感器，安装方向正确、转子能够转动，实际流速达到该型号的起测条件。
3. 有水时分别测传感器信号输出端和从机 GPIO5 对共地的波形。GPIO5 应收到符合 3.3 V 输入规格的高低电平和下降沿；不能凭线色或供电电压推断信号电平。开集电极/开漏输出的上拉及推挽输出的电平转换按型号确定。
4. 传感器端无脉冲：检查传感器供电、转子/流向和传感器本体；传感器端有、GPIO5 无：检查线束、接点、共地和电平接口；GPIO5 已有合法脉冲但 raw 不增：再定位 GPIO 配置、中断注册和 ISR 执行，必要时在隔离水路控制输出的台架上输入已知 3.3 V 测试脉冲核对计数。

恢复脉冲后再核对实测水量和 k。修改 k 或延长无流量等待不能解释或解决本次累计计数不增长的问题。

## 6. Mesh 与故障时序

**通信有异常迹象，但当前证据不能定位到特定 SDK 或射频原因。** 主机与从机均注册 CE（LeaseAck）及 D5（StartOK）opcode，格式和接收允许列表包含这些消息；首个 seq=22 已实际接收应用，未发现固定格式不兼容导致全部 ACK 被拒的问题。

seq=23/24 的从机 `event=1/err=0` 仅表示本地协议栈接受发送，不是对端应用确认；`trace_lost=0` 也不是无线零丢包证明。进一步定位需要短窗口记录从机业务 ACK 内容、主机 model callback 收到的 opcode/source/length、格式与来源过滤结果及队列丢弃，按 epoch/seq 对齐，并配合 RSSI/射频抓包。当前缺少这些底层接收证据，不能把缺失直接定为 Mesh 容量不足、队列溢出或特定广播碰撞。

`R.reason=LEASE` 而 `FLOW.reason=NO_FLOW` 并非自动说明 APP 解析出错：`MasterScheduler::stop()` 在主机触发停止时保存总原因，进入 Draining 后保留该原因；晚到的从机 Result 仍记录从机的本地 NO_FLOW 原因。该代码行为能够解释两种原因共存，但 315:76/81/82 缺少完整过程日志，不能逐次证明首触发的时序。315:77/78 的 TRANSPORT 也缺少首触发 guard/队列现场，可能入口应通过后续日志区分。

另有已确认的架构时序限制：从机 `ValveMeshSession::poll()` 只对 TARGET 关阀发送紧凑 TargetClosed；`Application::status()` 只发送 Done/Fault 终态。**NO_FLOW 关阀后须等 500 ms 静默结算，再通过分段 Result 通知主机。** 本次 Result SAR 用时 738 ms，主机停泵发生在接到该结果之后。PC 接收两端关阀/停泵日志的时间相差约 1.24 秒，但这不是同步硬件测量值。若最后一路阀已关闭，主机获知关闭存在等待窗口；应评估将“已关闭/故障”即时紧凑通知与最终计量结算分开，保留现有租约保护。

本次还观察到 ResultAck C7 的一次 SAR 结束耗时 **2500 ms**，后续 ACK 排队 **1700 ms**。这些是终态确认阶段的真实延迟样本，不能与 NO_FLOW 首触发混为一谈，也不足以计算长期故障率。

## 7. 稳定性及验收边界

90 秒采集内未观察到栈溢出、看门狗、Brownout 或 reset banner。主从 Mesh 健康快照为 1，faults/expired=0；主机 BTC 最低剩余栈 2988 字节、heap_min=79688。该观察窗口没有复现昨日的 BTC 栈溢出，但不能代替长时稳定性验收。

主机启动以来累计 `tick_max_ms=73`，超过既有 50 ms 门槛；从机为 50 ms。主机 73 ms 在本次任务开始前已存在，不能归因于本次任务。主从历史 SAR 最大值及从机 hello_timeout=1 也为累计记录，不能逐次对应到表内某个任务。当前仍不能标记单路定量或多路并发实水验收通过。

原始采集开始存在 COM3 乱码/重复片段，另有读取超时拆行；分析器标记一条空闲 HelloReply ticket=134 的不完整 mesh_tx 行。关键任务 315:83 的启停、HALL、命令重试与首租约证明记录完整可读，但本报告不据此声称串口记录或无线交付绝对无遗漏。
