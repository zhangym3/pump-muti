# ESP32-C3 Mesh 配置卡在“正在绑定密钥和配置 Mesh”修复方案

## 实施与实机结果（2026-10-24）

软件修复已实现并部署到 COM9 主机，Build ID `6df368c4`；主机 NVS 保留，启动 epoch 从 41 增至 42。COM6 从机未刷写，Build ID `f0f1957d`。生产主机固件 SHA256：`f65de99ba95949fb50d175db98670c7751add9dfe7605a0e29faee85381936e5`。

- 主机 host tests：33 组通过，含 Mesh 集成模拟；固定 SDK 回归和架构边界检查通过。
- Android `testDebugUnitTest assembleDebug` 通过；步骤/重试进度 UI 已构建。
- 对已保存节点 `0005` 只执行一次 `mesh-retry 42 9304 0005`。三次 Composition Data Get（attempt 1～3）均未收到完整状态；日志出现 `Incomplete timer expired`，每次均等待 SDK 超时后延迟 12 秒，最终在 attempt 3 进入 `FAILED/CONFIG_TIMEOUT`，没有无界重试。
- 最终主机状态：`busy=0`、`step=1`、`attempt=3`、`restart_required=0`；节点 `0005 online=0 commissioned=0`。主机 PWM `output=0`；从机本地阀门 `output=0`、`valve_command=0`。没有清 NVS、mesh reset/join/commission 或泵阀动作。
- 因从机响应仍出现 SAR incomplete，本轮软件修复验收通过，但现场配网验收未通过。首个无线丢段原因仍未区分；用户暂时无法断开外设，故供电/外设隔离 A/B、空中/HCI 抓包和连续 3 次成功通信检查均未完成。不要把本轮描述为稳定配网成功。

## 目标

修复主机发现并完成 PB-ADV 配网后，配置阶段长时间停留在 `CONFIGURING`、反复出现 `CONFIG_TIMEOUT` 的问题。第一阶段针对已发现的软件重试放大因素；若单次响应仍丢失，再用分阶段诊断区分 Mesh 分段收发与硬件/RF 原因。

本方案不清除 Mesh NVS、不重置从机、不重新配网已有节点，也不触发泵阀动作。配置修复只作用于主机；从机先保持当前已验证的普通固件，减少同时变更的变量。

## 当前证据与判断

- 2026-10-23 的双端诊断日志显示，从机对 Composition Data Get 发送三段响应；主机分次只收到部分段，从机收到部分 ACK 后继续重传，最终重传耗尽。
- 2026-10-24 普通固件也复现 `Incomplete timer expired`、`Duplicate SDU`、重传耗尽和配置超时。Composition 有一次完整成功，随后 AppKey Add 仍超时，说明链路间歇可用，但不稳定。
- 主机 `src/mesh_management.cpp` 当前配置客户端 `msg_timeout=4000`；配置失败后最多重试 3 次。SDK 的不完整分段重组超时下限约为 10 秒，可能随 TTL 和已收段数增长。过早发起同一节点的新请求，可能在上一响应的 SAR 重组仍有效时打断它。
- 代码还有 7 秒主循环兜底重试。它与配置客户端超时回调分属两条触发路径，逻辑难以审计，也可能造成重复提交或重复处理超时。
- 因而已确认的首要软件修复点是：停止短于 SAR 接收窗口的请求重试，并保证任一时刻只有一个配置事务在途。
- 初始丢段的来源仍未确定。现有证据不能区分射频干扰、板上控制器收发、供电波动、天线布局或外设影响；外设隔离和空中/HCI 抓包尚未完成。没有证据支持 AppKey 内容错误或 Composition 模型不匹配。

详细原始证据见 [PAIRING_DIAGNOSIS_20261023.md](PAIRING_DIAGNOSIS_20261023.md) 中“配置响应超时的更深层根因链”。

## 修复设计

### 1. 配置事务只允许一个重试调度器

在主机配置状态机中明确记录当前步骤、尝试编号、发送时间、响应截止时间和是否等待 SDK 回调。配置客户端超时回调只入队并记录结果；唯一的状态机负责决定继续、延迟重试或失败。

合并/移除当前 7 秒兜底与 SDK 回调中的独立立即重发路径，避免两处代码各自推进同一步骤。每个超时事件必须匹配目标地址、当前 opcode 和当前尝试；迟到或重复回调只记日志，不得推进已经改变的步骤。

### 2. 等待时间覆盖 SAR 重组窗口

首个验证版本将每次配置状态响应超时从 4 秒提高到至少 15 秒，并在发送前核对固定 SDK 版本的 `incomplete_timeout()` 公式，确保等待时间不短于实际最坏 SAR 不完整窗口。若该 SDK 配置算出的窗口超过 15 秒，则按公式提高等待值并设置明确上限；不得仅凭“通常 10 秒”假定足够。

状态响应超时后不立即重试。SDK 超时回调是唯一的请求超时来源，因为 SDK 会按分段请求的发送重传时间动态扩大超时；应用不能用一个更短的固定兜底计时器抢先重发。收到 SDK 超时后再等待至少 12 秒（高于当前 Composition Page 0、TTL=3、三段响应时的 10.9 秒不完整重组窗口）才重试。每一步最多 3 次，超过后转入 `FAILED/CONFIG_TIMEOUT`，释放 busy 状态并向管理端报告当前步骤与尝试数。若 Composition 响应长度、TTL 或 SDK 超时公式变化，应重新计算清理间隔。持续时间应可观测且有上限，不能永久显示配置中。

如果 SDK 的 config client 本身会在 `msg_timeout` 内管理分段发送/应答等待，应以该 SDK 实际语义为准，避免同时在 SDK 层与应用层对同一消息重复重试。提交前检查调用链和超时回调时序，并把最终重试策略写成单一、可测试的状态转移。

### 3. 处理“命令已执行但状态回复丢失”

超时表示没有收到状态响应，不等于从机没有执行 AppKey Add、Model App Bind 或 Subscription Add。恢复流程不得把超时直接解释成密钥错误，也不得要求清网。

重试前按 Mesh Config 状态机语义验证每一步的幂等性。对可能已执行的配置操作，优先通过可用状态查询或目标节点状态核验结果；若协议/API 无法查询，则确认重复下发同一参数的返回语义，并将“已存在/已绑定”作为可判定的成功结果处理。只在状态明确不匹配时继续修复该步骤。

### 4. 进度和诊断日志

每次发送记录 `address`、`step`、opcode、attempt、单调时钟时间和 SDK 提交结果。每次回调记录事件类型、error、valid、耗时和是否匹配当前事务。状态变化记录 `CONFIGURING` 的子步骤；最终失败记录具体步骤和原因。

在固定 SDK 的 Mesh SAR 收发日志中，增加或启用足以关联配置事务的诊断字段：SeqAuth、段号/总段数、ACK 位图、源/目的地址和重传次数。避免输出 AppKey 明文、设备密钥或可复用凭据。

管理端/UI 应显示 Composition、AppKey、Model Bind、Subscription 等当前步骤，并显示有限重试/超时结果。最终成功以配置状态机进入 `WAIT_HELLO` 后收到目标从机 HELLO，达到 `commissioned=1` 且 `online=1` 为准；不能仅凭 UI 离开“正在绑定”或节点短暂 online 宣告成功。

## 实施步骤

1. 固定当前普通主机/从机 Build ID、有效 `sdkconfig`、Mesh 地址和只读状态快照；确认目标从机已配网时走 `mesh-retry`，不执行 `mesh-join` 或 mesh reset。
2. 在主机配置状态机中合并超时处理，加入事务匹配和单一重试调度；按 SDK SAR 超时公式设置等待值及有界退避。
3. 增加状态转换与迟到/重复回调测试，覆盖各配置步骤成功、首次超时后成功、三次耗尽、旧回调到达、重复超时事件、地址/opcode 不匹配、跨毫秒计时回绕，以及执行成功但回复丢失后的恢复路径。
4. 运行主机控制/Mesh 测试、SDK 一致性和架构边界检查；构建普通主机固件。记录 Build ID、构建配置摘要和产物哈希。首轮不改从机固件、不烧诊断固件。
5. 先做只读设备状态核对，再经用户明确指示烧录主机。保留 NVS；串口采集配置流程，不触发泵阀动作。
6. 对现有已配网节点执行一次有限 `mesh-retry`。采集完整主机日志；若固件具备只读从机日志，也同步采集。每轮最多执行一次管理请求，禁止脚本自动无限重试。
7. 若软件修复后仍见 SAR 段/ACK 丢失，再单独安排硬件对照。当前用户暂时无法断开外设，因此先记录该限制，不将硬件因素定为根因；条件允许时以仅 USB 供电、外设断开的 A/B 对照作为后续阶段，不与软件变量同轮修改。

## 验收标准

### 软件与构建

- 任意时刻目标节点只有一个配置请求事务在等待；同一超时不会从回调和 tick 各重发一次。
- 单步响应等待不短于所用 SDK 配置下的 SAR incomplete 窗口；重试次数和总耗时有明确上限。
- 迟到、重复、地址不匹配或 opcode 不匹配的回调不会推进状态机。
- 自动化测试验证超时重试、幂等恢复、成功路径和失败收敛；规定的主机测试及构建检查全部通过。

### 现场

- 保留当前 Mesh 节点记录和 NVS，成功完成 Composition、AppKey、Model Bind、Subscription 配置。
- 从机收到配置后能向主机发送 HELLO；主机状态最终为 `commissioned=1`、`online=1`，且没有 `restart_required`。
- 整个配置期间没有启动泵阀；主从控制输出保持关闭。
- 连续重试时若仍发生响应丢段，系统必须按有界策略明确进入失败，日志能指出失败步骤和 SAR 证据，不再无限显示“正在绑定密钥和配置 Mesh”。
- 实机至少连续完成 3 次只读状态核对/通信检查，确认不是单次短暂在线。若只完成一次，记录为“单轮通过”，不宣称稳定性验收完成。

## 风险与回退

- 等待时间增长会让一次失败需要更久才能反馈；这是给 SAR 重组留出时间的代价。通过进度显示、最大重试次数和总超时控制可避免无期限等待。
- 若单次完整响应仍丢失，增加等待只能消除过早重试造成的放大，不能修好最初的链路丢包。此时保留日志，进入射频/供电/外设分阶段诊断。
- AppKey 或绑定请求可能已在从机执行而仅回复丢失，因此升级后重试应针对现有 Mesh 地址并验证状态，不能以清除两端网络作为恢复手段。
- 若新固件导致配置阶段无法推进，可恢复先前已记录的主机固件版本；烧录时保留 NVS，停止进一步管理重试。回退后重新读取地址、commissioned、online 和控制输出状态，不以刷写成功代替运行状态验收。
