# 恢复资源预算与 G0 验证边界

状态：2026-10-27，源码候选。容量配置和 host SDK 测试已补齐；逐绑定 AppKey 分配、撤销与对账仍未接入运行时，G0 尚未通过实机验收。

## 主机密钥预算

`recovery_resources.h` 预留 8 个 Provisioner AppKey 和 8 个模型绑定槽：5 个当前设备绑定 + 1 个既有共享密钥 + 1 个串行恢复中的待提交密钥 + 1 个隔离记录密钥。新增隔离项可能耗尽余量，协调器必须在从机退网前检查预留条件并返回容量错误；不能通过驱逐其他绑定、复用旧密钥或静默清隔离项腾位置。

`sdkconfig.master.defaults` 和当前各 `sdkconfig.pump_master*` 的 Provisioner/model 容量均调整为 8。已有 sdkconfig 优先于 defaults，因此 `mesh_transport.cpp` 在编译时检查两项容量；任一小于预算即拒绝构建。业务登记仍最多 5 台，并发仍为 1。节点角色自己的 AppKey 表与 Provisioner 表是 SDK 中的独立数组；本次不扩大从机容量，也不将主机节点角色的表误算为 Provisioner 容量。

资源预算只解决固定数组上限，不能证明已有登记、事务、地址隔离和 NVS 的原子预留正确，也不表示现有 `app_idx=0` 路径已经替换。后续必须让发送、接收过滤、配置、持久化和撤销统一使用绑定映射。

## SDK host 验证

`tools/run_sdk_tests.py` 从哈希锁定的真实项目 SDK 提取 AppKey 添加、索引/密钥查找和模型绑定共 6 个函数，保留实际 AppKey 结构，依次测试 `(Provisioner表, 模型表)=(2,3)、(8,3)、(8,8)`。

覆盖耗尽、完整表上幂等、索引冲突、无效网/模型、内存分配/RNG/AID 失败、索引高水位耗尽，并核对已有密钥/模型绑定未被覆盖、无分配泄漏。8/3 案例明确表明只扩大 Provisioner 表仍会卡在第 4 个模型绑定。

实际 SDK 按密钥字节去重，可能在请求另一个 net_idx 或 app_idx 时返回旧索引并报告成功。此处没有修改 SDK 语义；后续协调器必须对账返回的实际索引、所属网络及预留记录，不能把成功回调直接当作本次资源已就绪。测试材料全部为合成密钥，不写日志中的密钥值。

分配、密码 AID、NVS 提交和模型查找的外围在 host 测试中为 stub。该结果不能替代真实 SDK 初始化、重启后密钥/模型恢复、空口配置、设备堆内存和 NVS 容量验收。

## 只读实机采样

主从候选均提供 USB-only 的 `recovery-resources` 命令。它不读出 NVS 键或值，不清网、不写存储、不改变输出，返回：

1. `RECOVERY_RESOURCES`：NVS 状态、总条目、使用条目、空闲条目、可用条目及 namespace 数量。`free` 包含保留条目，不能代替 `available`；`nvs_err!=0` 时不能将部分统计作为有效容量证据。
2. `RECOVERY_HEAP`：内部 8-bit heap 当前空闲、历史最小空闲及最大连续块。
3. `RECOVERY_LIMITS`：编译后 Provisioner/model/node 密钥上限与 RX SDU、TX segment 配置。

每次采样须关联本次 build、设备身份和时间。当前值不等于最坏情况：仍须在 5 台登记、隔离项、恢复 journal、Mesh 设置、bond、重复重配和 GC 共存时测量，完成真实分区满、掉电及重启验证。不能因为当前还有空闲条目就标记 G0 通过。
