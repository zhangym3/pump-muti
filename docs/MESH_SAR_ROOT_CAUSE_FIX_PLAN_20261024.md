# ESP32-C3 Mesh 配置不稳定的根因修复方案

日期：2026-10-24\
适用设备：ESP32-C3 主机 COM9、从机 COM6\
目标：定位并消除 Mesh 配置期间分段报文（SAR）或确认帧丢失，保证配置流程在有界时间内稳定完成。

## 1. 结论摘要

当前证据支持的最深层故障位置是 Bluetooth Mesh 分段收发/确认往返不稳定。应用曾在 SAR 尚未完成时过早开始下一次配置请求，这会清除或替换 SDK 中尚未完成的接收上下文，是已确认的软件放大因素。主机当前已采用较长响应等待和 12 秒重试退避，消除了已知的 4 秒快速重试路径，但最新日志仍记录到分段重传耗尽和 `Incomplete timer expired`。因此仅增加等待时间不能根治底层报文丢失。

最新一轮配置请求 `609943647` 最终走完 Composition、AppKey Add、Model App Bind、Subscription Add，状态进入 `READY`，从机 `0005` 最终 `online=1`；整个过程中主机 PWM 输出为 0。与此同时，该轮多次出现 `Ran out of retransmit attempts`、若干配置状态超时，以及最终 READY 后的 `Incomplete timer expired`。由于日志目前没有把 SDK 的 SeqAuth、分段号和 ACK 位图关联到配置事务，READY 之后的告警不能直接归因到某一步配置，也不能证明已稳定。

目前不能从日志判定最初丢失发生在主机接收、从机接收、ACK 返回、控制器/SDK 调度，还是 RF/供电/外设环境。外设隔离 A/B 尚未进行，故物理原因仍待验证。没有证据支持 AppKey 内容错误、设备密钥错误或 Composition 模型不匹配。

### 2.1 直接观察到的现象

- Composition Data Get 在前两次尝试超时，第三次取得有效响应后继续配置。
- AppKey Add 第一次超时，第二次取得有效状态。
- Model App Bind 首次成功。
- Subscription Add 前两次超时，第三次成功。
- 多次从机串口出现 `BLE_MESH: Ran out of retransmit attempts`；主机出现 `BLE_MESH: Incomplete timer expired`。
- 配置完成后状态机已为 `READY`，节点 `online=1`，但 `commissioned=0`。后者是安全启用标志，不是 Mesh 配置失败。

### 2.2 根因边界

已证实：Mesh SAR 传输期间有未完成的分段/确认，且旧的短配置超时会造成过早的新请求。\
尚未证实：具体丢包方向、RF 干扰源、供电跌落、外设影响、天线/板卡问题、SDK 控制器缺陷或某个重发参数是首要原因。\
不能作出的结论：不能把 `Ran out of retransmit attempts` 单独解释成“从机没有收到请求”；它表示该设备作为发送端的分段消息没有在发送重试预算内得到完整确认。需要关联段号和 ACK 位图才能判断具体报文。

## 3. 修复原则

1. 一轮实验只改一个因素，主从固件、供电、摆放、手机连接状态均记录 Build ID 和实际配置。
2. 始终复用地址 `0005` 和当前网络状态。禁止以清 NVS、Mesh reset 或重新入网作为诊断手段。
3. 不发送 Commission、泵、阀或测试输出命令。验证期间控制输出必须保持 0。
4. 先补足可关联的双端日志，再调 Mesh 重发或硬件环境。不能用成功一次代替根因验证。
5. SDK/控制器调参先用诊断构建做 A/B；验证通过后再合入普通固件。
6. 所有日志不得记录 AppKey、DevKey、NetKey 明文或可重放凭据。

## 4. 阶段 A：固定基线并补齐证据

### A1. 只读基线采集

每轮开始前记录两端 Build ID、有效 `sdkconfig` 摘要、主从 Mesh 地址、主机节点 inventory、节点 `online/commissioned`、主机 `pump_command`/PWM、从机阀命令与输出。确认手机连接状态、USB/外设接线、板间距离、板载天线方向和附近金属物。

不得因某个状态为 `online=0` 而自动删除节点。配置期间不执行扫描、重配网、reset 或其他 Mesh 管理命令。

### A2. 给配置事务与 SAR 事件建立关联

在主机管理代码和本地 Mesh SDK 诊断日志中增加/整理以下字段：

- 应用侧：管理 request ID、目标地址、配置 step、opcode、attempt、SDK 提交结果、发送时间、回调时间、回调类型、错误码、是否匹配当前等待事务。
- Mesh SAR 发送侧：本机地址、对端地址、SeqAuth/SeqZero、Segmented/Unsegmented、SegO、SegN、发送轮次、重发原因、最后 ACK block 位图、最终完成/耗尽结果。
- Mesh SAR 接收侧：源/目的地址、SeqAuth/SeqZero、SegO、SegN、收到段位图、重复段、ACK block 位图、接收上下文分配/清理原因及时间。
- 时间戳：应用单调时间和 SDK uptime；记录各端启动 epoch，以免跨重启误关联。

只记录必要元数据，不打印加密前 Access Payload、密钥或凭据。将“超时”区分为 SDK 消息状态超时、SAR ACK 重试耗尽、SAR incomplete timer 到期、应用总流程超时。

### A3. 证据门槛

至少采集一轮从 Composition 开始到 `READY` 或明确失败的主从同步日志。日志应能回答：

1. 哪个节点发送了分段消息？
2. 两端分别收到了哪些段？
3. 哪个 ACK block 被谁发出/接收？
4. 最后一次重发耗尽发生在哪个 SeqAuth？
5. `Incomplete timer expired` 对应哪个源、目的地址和重组上下文？

若仍无法回答，先修诊断信息，不进入调参阶段。

## 5. 阶段 B：软件侧稳定性修正

### B1. 保持现有超时保护并复核 SDK 语义

主机现有配置管理采用单请求状态机、较长 SDK 响应等待、超时后延迟 12 秒再重试、每步最多 3 次。保留有界策略，同时依据当前固定 SDK 的配置状态回调和 SAR 超时计算复核两个时间：

- SDK 的 `msg_timeout` 是否覆盖该配置消息的分段发送与状态响应过程。
- 应用层退避是否晚于旧 SAR 接收上下文清理窗口。

禁止另加短于 SDK 的独立 watchdog 去触发同一步重发。若 SDK 超时回调和应用状态机能同时触发同一尝试，先合并成唯一重试调度器。每次迟到/重复回调只记录，不推进新 step。

### B2. 配置期间降低非必要空口流量

增加仅用于诊断的“配置静默”模式：主机和从机在 `CONFIGURING` 期间暂停非必要周期性 Vendor Model 上报/HELLO 重复发送；保留 Config Server 响应、Mesh SAR ACK、安全状态、必要的故障消息和维持在线所需的最低流量。配置结束、失败或取消时恢复原周期。

测试只改变是否启用静默模式，比较同一地址、同一距离、相同外设和供电条件下：配置超时数、SAR 重试耗尽数、每 step 耗时及状态成功率。若无统计改善，不保留此改动作为生产修复。

### B3. 幂等恢复

AppKey Add、Model App Bind、Subscription Add 超时不代表设备端未执行。对每步确认重复下发同参数时 SDK/设备状态语义；若能通过状态查询确认已完成，则直接推进，不要清网或改密钥。若无法查询，记录超时并在下一次有限重试后验证完整配置及 HELLO。

## 6. 阶段 C：Mesh 网络重发参数 A/B

当前主从 `net_transmit` 均为 1 次额外重发、20 ms 间隔。它可能影响普通 Network PDU，也会影响分段 ACK 等网络控制消息。改值可能提升丢包容忍度，也可能增加广告拥塞，因此不直接把“重发更多”定为最终方案。

### C1. 实验控制条件

- 使用隔离诊断构建，保留普通固件作为可回退基线。
- 现有 NVS、地址、密钥、TTL、扫描去重、功率、手机连接状态及物理位置全部固定。
- 每组至少 5 次有限配置验证或等量只读的可关联 SAR 测试；每次最多发起一个管理操作，不自动循环重配。
- 同时记录配置总时长、每步 attempt、每个 SeqAuth 的段/ACK 结果、CPU/队列状态和控制输出。

### C2. 对照顺序

| 组别 | 主机 net transmit | 从机 net transmit | 目的 |
|---|---|---|---|
| A | 1 次，20 ms | 1 次，20 ms | 当前基线，重建统计 |
| B | 2 次，20 ms | 基线 | 单独观察主机发送/ACK 侧变化 |
| C | 基线 | 2 次，20 ms | 单独观察从机发送/ACK 侧变化 |
| D | 2 次，20 ms | 2 次，20 ms | 只有 B/C 有改善或方向仍双向不明时再测 |
| E | 按前组胜出方向固定重发数，仅把间隔改为 40 ms | 同左或基线 | 单独评估间隔，避免和重发数混为一个变量 |

表中的 2 次/20 ms、40 ms 是候选实验值，不是已验证的量产推荐值。若某组广告拥塞、广播队列增加、应用延迟恶化或 SAR 成功率无提升，停止该组并回到 A。

### C3. 参数保留条件

候选参数必须在至少 5 次试验中明显减少 SAR 未完成/配置状态超时，且没有增加控制命令延迟、队列压力或其他 Mesh 故障。若改善只来自主机或从机单边参数，量产配置只改已证明有效的一端。通过后再做不少于 20 次配置/状态通信回归，覆盖手机 BLE 连接和未连接状态。

## 7. 阶段 D：射频、供电和外设隔离

当前无法断开泵阀外设，因此本阶段为条件允许后的必要验证；在完成之前，不把硬件环境排除为根因。

### D1. 环境记录

记录主从板卡型号与天线形式（PCB 天线/外接天线）、天线端方向、板间距离、USB 线和电脑位置、附近金属面、泵阀电源、驱动器和电磁阀线束布局。外设电源和 USB 供电是否共地也要注明。

### D2. 分组对照

每次只改变一个因素，使用阶段 A 中已验证的日志和固定固件：

1. 当前完整接线，USB 供电，50 cm：复测基准。
2. 保持板间位置和 USB 不变，断开泵阀/传感器信号线及其独立电源，只留两块板 USB：判断外设/电源噪声贡献。
3. 恢复接线，仅将两板拉至 1–2 m、天线方向互相无遮挡：判断近距离耦合/摆放影响。
4. 保持其他条件不变，手机与主机 BLE 连接状态做 on/off 对照。
5. 若具备合适仪器，再观察 3.3 V 电源跌落、复位原因和 2.4 GHz 信道占用；仪器测量结果与串口错误按时间关联。

不要在同一轮同时改外设接线、供电、距离、Mesh 参数或固件版本。

### D3. 硬件整改判据

若外设隔离后失败率显著下降，应逐个恢复流量传感器、阀驱动、泵驱动和长线束，确定触发项，再处理电源分区/去耦、线束回流、驱动器续流/吸收、天线净空和地回流。阀线圈必须有适当的续流保护；泵电机按其驱动拓扑采用合适的抑制网络。整改后在完整接线状态做回归，不能只以隔离状态通过作为交付。

## 8. 阶段 E：SDK/控制器判别与结构性备选

如果阶段 A 已确认段/ACK 丢失，阶段 B 的静默和阶段 C 的受控重发均无改善，而阶段 D 在仅 USB 条件下仍稳定复现，则进行 SDK/控制器判别：

1. 固定硬件与 Mesh 网络参数，对比当前固定 ESP-IDF/Bluetooth Mesh SDK 与一个经项目兼容性验证的更新 SDK；单独构建主从匹配版本。
2. 仅在可回退诊断板上运行相同 SAR 测试，核对 segmented RX 上下文、ACK 延迟、广告发送完成回调和控制器队列错误。
3. 如果 SDK 新版修复或显著降低失败，移植修复并跑完整控制/Mesh 测试、内存和任务栈检查，再安排实机验收。
4. 如果平台控制器仍无法达到要求，再评估改变配网/管理承载或更换无线硬件。该项属于架构备选，需单独确认手机兼容、双角色能力、产品功耗和安全边界；不作为本轮直接改造。

## 9. 验收标准

### 代码与诊断

- 一节点同一时刻最多一个配置请求在途；所有重试由一个状态机决定。
- 迟到/重复/地址或 opcode 不匹配的回调不改变流程状态。
- SAR 日志可由 SeqAuth/SeqZero、源/目的地址、段位图和 ACK 位图关联；不包含可复用凭据。
- `CONFIGURING` 有当前 step、attempt 和剩余等待时间；失败明确显示阶段和原因，不会无限停留。
- 主机控制/Mesh 测试、SDK 一致性检查、架构边界检查和对应从机测试通过。

### 实机

- 在完整产品接线和供电条件下，连续 20 次目标地址配置/状态通信均在有界时间内完成；若无法重复配置已有节点，则使用同样的分段收发强度和双向状态操作替代，并记录覆盖范围。
- 每次完成时主机状态为 `READY`，节点 `online=1`，没有 `restart_required`；期间不能出现归属目标 SeqAuth 的 `Ran out of retransmit attempts` 或 `Incomplete timer expired`。
- 每轮至少再做 3 次只读状态核对/HELLO 往返，确认不是瞬时 online。
- 所有验证期间主机泵 PWM 与从机阀输出保持 0；从机 `commissioned=0` 可保持，不得为验收自动启用。
- 任何一轮失败均保留证据并按阶段继续，不清 NVS、不换密钥、不清网来掩盖问题。

## 10. 回退与停止条件

- A/B 固件与参数必须保存 Build ID、源代码版本、`sdkconfig` 摘要和产物 SHA256；任何异常立即停止后续操作并刷回已记录的普通固件，保留 NVS。
- 发现泵/阀输出变化、设备复位、节点表变化、意外 mesh reset/provision、控制队列异常或串口日志无法关联时，立即停止实验，不继续重试。
- 任一参数组若使广播量、队列延迟或控制响应变差，回退该参数，不把“偶尔连通”作为保留理由。
- 只读状态核对不等同于配置修复；一次 READY 只记作单次通过。

## 11. 建议执行顺序与交付物

1. 归档当前两端日志和基线快照；输出阶段 A 可关联 SAR 事件的诊断构建。
2. 先完成静默模式 A/B，确定是否有非必要应用流量竞争。
3. 若仍有丢段，按 C1–C3 次序逐项测试主从 `net_transmit`，选出有数据支撑的候选参数；不凭直觉一次修改两端多个值。
4. 外设可断开时执行阶段 D；若隔离有效，针对逐项恢复时发现的噪声源做硬件整改。
5. 仅在低流量、候选重发参数和硬件对照都无法解释/解决时进入阶段 E。
6. 每阶段交付：实验配置表、原始双端日志、事件关联表、失败率/耗时统计、固件 Build ID 和是否通过的判定。

当前允许的安全动作仅限只读采集和对现有 Mesh 节点的有限配置/状态诊断；此方案不授权清网、重新配网、Commission、泵阀输出或其他不可逆设备操作。
