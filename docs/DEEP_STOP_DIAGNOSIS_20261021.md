# 异常停止深入诊断（2026-10-21）

## 1. 结论

用户新提供的 COM4 日志完整记录了从机任务 **315:87**：阀输出开启 5000 ms 后，由 **无首脉冲保护 `NO_FLOW`** 主动关闭；随后静默结算 500 ms，进入 FAULT。7 个 HALL 快照全部为 `raw=0、delta=0、last_ms=0`，任务计数也为 0。直接停止条件已经确定，但“为什么没有新增被接受的下降沿”尚未定位到信号源、GPIO 输入或中断中的具体环节。

现场已确认连接正常，且此前确认泵阀动作、有出水。本报告采用这些现场信息，不再将接线问题当作已证实结论。连接正常不能替代 GPIO5 实际波形及中断采集验证；0 mL 是计数结算值，不能解释为实际没有出水。

另用当前真实控制代码复现了两个时序问题：**启动回执等待会挤占 5 秒首脉冲窗口；NO_FLOW 关阀后的 STALE 租约回执可能让主机先记录 LEASE，从机仍记录 NO_FLOW。** 两者不能解释输入计数为什么始终为 0，也不能据此认定每次历史 LEASE 都由同一路径触发。

开头的 `Hard resetting via RTS pin`、DTR/RTS inactive 是烧录/监视工具输出的复位与串口控制提示，不是 ESP32 的运行期崩溃报告。任务执行前后 uptime 持续递增，所贴片段未见 panic、watchdog、brownout 或新的 reset banner。只能说明这个观察窗口没有这些证据，不能用于排除窗口外的重启。

本次重启后的 raw=0，与前一个启动周期累计 raw=253 不矛盾：原始累计计数保存在 RAM，不能跨重启相减。所贴日志没有固件 build 行，不能直接假定它与此前核验的 build `586bb591` 完全相同。

`mesh healthy=1、faults=0、expired=0、trace_lost=0` 表明未记录到对应的本地发送治理故障；它们不证明主机收到每条消息。`event=1/err=0` 是本地协议栈接受发送，不是主机应用确认。`event=3` 是本地 SAR 结束记录，不等同于业务处理成功。此处只有从机日志，无法确定任务 315:87 的主机实际启泵时刻、最终总原因或空口丢包率。

## 3. 真实代码复现

诊断程序 [deep_stop_probe_20261021.cpp](../tools/diagnostics/deep_stop_probe_20261021.cpp) 复用现有 Mesh 仿真台架，直接链接实际 `MasterScheduler`、`PumpSafetyController`、`FlowJobController` 和实际会话/发送治理代码。没有重写一份简化控制算法。它不接触设备，也不覆盖真实 GPIO ISR、无线链路、传感器波形或水路。

### 3.1 累计计数与速度

在起始累计 raw=253、任务期间无新增输入的情况下，50%、75%、100% 三档均在开阀 5000 ms 后触发 NO_FLOW，任务脉冲为 0。模拟新增 12 个脉冲时，raw 变为 265、任务脉冲为 12、状态进入 RUNNING；随后 1500 ms 没有新增脉冲才触发运行期 NO_FLOW。

这证明当前控制器不会把本任务新增计数全部被 baseline 抵消；它不证明现场 GPIO ISR 正常。`speedFactorPermille` 目前被校验和保存，但没有用于调整从机的 5000/1500 ms 保护时间。三档 PWM 不代表实际水量严格成 50/75/100% 比例；低速启动、排气和起测条件必须实测。

### 3.2 开阀与启泵之间存在计时偏差

从机 `start()` 在读取 baseline、发出开阀输出时，设置 `openedAt_`。主机须在 StartOK 和新鲜 LeaseAck 证明到齐后才允许启泵。首脉冲保护因此从开阀计时，包含尚未启泵的等待。

| 仿真注入的 StartOK 延迟 | 开阀 t | 启泵 t | NO_FLOW 关阀 t | 启泵后至关阀的窗口 |
| ---: | ---: | ---: | ---: | ---: |
| 0 ms | 265 | 345 | 5265 | 4920 ms |
| 1500 ms | 265 | 1850 | 5265 | 3415 ms |
| 3800 ms | 265 | 4150 | 5265 | 1115 ms |

这是代码路径及边界复现，不是现场启动延迟的测量。新日志中第一条可见 LeaseAck 在开阀 1594 ms 后提交，能看到明显的握手等待；不能把该提交时刻直接当作主机启泵时刻。此前双端捕获的任务 315:83 则明确记录了首个 START 提交至主机启泵为 1665 ms。

风险：如果实际首脉冲在开阀 5 秒之后才出现，当前设计会先停止，即使泵已工作一段时间。这是需要修正的计时设计问题；目前尚无现场首脉冲波形时间，不能断言它就是本次 0 计数的最终根因。单纯放宽保护也不能解决始终没有输入的情况。

### 3.3 LEASE 可以由 NO_FLOW 之后的回执触发

仿真中无输入导致从机在 t=5265 关阀；主机在 t=5390 接收关闭后产生的 STALE LeaseAck，即刻停泵并记录 LEASE。此时距离最后有效租约证明不足 8 秒。晚到 Result 被正常对账，从机仍为 NO_FLOW，主机保留首次停止原因 LEASE。

该路径在未注入丢包的默认仿真中已出现；另一个用例主动延迟 Result，使 STALE 先到，得到相同结果。因此 **主机 LEASE 不一定表示“8 秒内没有收到租约回执”**，也可能表示“收到明确拒绝续租的 STALE 回执”。

当前 `ValveMeshSession` 只对 TARGET 关阀提供紧凑 TargetClosed 通知。NO_FLOW 关阀后继续收到 Lease，返回的错误 ACK 多 1 字节：成功 ACK 为 8 字节，错误 ACK 为 9 字节，按当前 `MeshTxGovernor::segmented()` 进入分段路径；最终 Result 为 27 字节，也分段。

新日志里的 seq=39/40 分段 ACK 和超过 1 秒排队符合关闭后的错误回执路径，但日志没有打印回复枚举值，不能把它当作已解码 STALE，更不能推定其在主机上的到达顺序。Result 的本地 SAR 用时 1267 ms，也不是“从机关阀到主机停泵”的同步测量值。

风险：故障关阀后的通知等待与错误 ACK 分段，可能增加最后一路阀已关闭、主机尚未知情的时间，也会让两端停止原因不同。它发生在输入计数失败之后，应与首触发的 NO_FLOW 分开处理。

## 5. 后续修正与验收顺序

1. **定位输入链路**：同一受控低速任务中对照传感器信号端、GPIO5 实际波形和中断计数。GPIO5 有合法下降沿但 raw 不增时，才将问题收敛到运行期 pin mux、输入使能、中断类型/使能和 ISR；传感器有而 GPIO5 无时，才收敛到信号传输接口。仅看每秒 `level=1` 不能区分这些情况。
2. **改进诊断证据**：可为本地 `hall` 增加 GPIO 运行期配置、ISR 进入次数、被过滤次数；启动日志记录每个初始化步骤的 ESP 错误码。日志不走 Mesh、不在 ISR 内打印，不新增高频无线汇报。当前版本尚未加入这些字段。
3. **修正时间定义**：保持从开阀开始计量，同时为“等待启泵”和“启泵后等待首脉冲”定义各自有上限的保护阶段，保留独立最大开阀时间及租约。若需要新增启泵状态通知，应一并评审失包、迟到、重放和幂等规则，不能让任意续租无限延长首脉冲期限。
4. **缩短故障关闭通知**：评审通用紧凑 CLOSED/FAULT 通知，主机立即停止或移除已关闭支路，最终 Result 仍负责计量结算与原因对账。不能将 NO_FLOW 冒充 TARGET；主机还应记录 STALE 拒绝与 ACK 超时的不同触发证据。
5. 输入计数恢复后，再验证三档单节点首脉冲时间、断流 1500 ms 保护、定量精度、通信故障停止和最后一路关阀至停泵的同步延迟。当前不满足实水计量验收。

本轮没有修改或刷写业务固件，没有主动启停泵阀，也没有改变保护阈值。30 组主机核心测试、现有 Mesh 仿真套件及 8 个诊断用例全部通过；仿真通过不替代实水、GPIO 中断或无线验收。
