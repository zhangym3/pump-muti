# 任务 328:103 与重复停止按钮排查（2026-10-21）

## 结论

APP 任务卡和底部固定栏各有一个停止按钮，属于重复入口。现已删除任务卡内的按钮，仅保留跨标签页可用的底部停止栏。两处原按钮均由点击触发；本次设备结果记录为 `LEASE`，没有证据支持“重复按钮自行触发人工停止”。人工停止的业务原因应为 `MANUAL`。

本次任务目标为单路 250 mL、时限 240 秒，最终收到 **367 脉冲、62 mL**，主从均为 `FAULT / LEASE`。此次已经收到霍尔脉冲，不能套用早上任务的零脉冲 `NO_FLOW` 结论。租约保护的具体首触发路径尚未确定。

从机另外保留了停止后最终 `RESULT` 的分段发送超时，并因此进入发送治理冻结状态。该包只能在业务终态产生，不能将这次发送超时当作最初 LEASE 停止的直接原因。

从机保留的首个发送治理故障：

```text
MESH_FAULT first=1 reason=SAR_END t=11192080 ticket=1181 peer=0001 op=c5 err=-116 job=328:103
MESH_FAULT_TIMING first=1 issued=11189693 queued=11189693 in_flight=1 pending=2 seq=0 rev=1509
```

上述 `t` 均为从机 uptime（ms）。`op=c5` 为最终 RESULT，从提交到故障回调经过 2387 ms。当前 SDK `bt/esp_ble_mesh/core/transport.c` 在分段重传次数耗尽时以 `-ETIMEDOUT` 结束发送；工具链 `sys/errno.h` 定义 `ETIMEDOUT=116`，与此处 `err=-116` 一致。这表示本地分段发送超时，不能据此认定主机从未收到结果：主机当前已保存该任务的最终 FLOW，可能涉及重发或查询补取，现有快照不足以还原传递路径。

`diagnostic_ready=1` 表示退避后允许白名单诊断及终态结果等交互，**不表示业务发送恢复健康**；`restart_required=0` 也不等于自动解除冻结。`online=1` 仅表示近期可达，不代表从机可以正常接受新的业务任务。

手机前两次任务 328:101、328:102 均为 100 mL 目标，最终 601 脉冲、102 mL、`DONE / TARGET`。可见本轮异常与已有成功任务交错出现，不能归结为传感器始终没有输入。

## LEASE 的可能触发路径与证据边界

现场固件标识为主机 `71c9d8d6`、从机 `d5f97aca`；查询时已校验两工程 `.mesh-sdk/build.json` 中登记的输入哈希均与工作区一致。

1. 主机 [master_scheduler.cpp](../src/master_scheduler.cpp) 的 `leaseAck()` 将匹配租约的 `STALE` 回执映射为 `LEASE`；它不要求先发生 8 秒超时。
2. 主机运行期在有效租约证明超过 `LeaseAckTimeoutMs=8000` 后调用 `stop(LEASE)`，先停本地泵，再发 CLOSE。
3. 从机 `FlowJobController::lease()` / `tick()` 在本地 12000 ms 租约到期后关阀并记录 `LEASE`。从机收到主机 `CLOSE(LEASE)` 也会记录相同原因。

因此，主从最终原因相同不能区分“主机等待证明超时”“主机收到 STALE 拒绝”与“从机先租约到期”。需要运行期间双端租约序号、发出/收到时间、回执值、首个停泵/关阀触发记录。目前没有这段完整时序，也没有证据证明实时流量单播是本次停止的原因。

最终 RESULT 的 SAR 故障发生在关阀结算之后，是另一个已证实的回传问题。发送治理冻结会阻断后续正常业务，应单独处理，不能靠放宽租约阈值掩盖。
